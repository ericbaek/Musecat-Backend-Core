# Developer Center: self-service partner registration and one-click activation

Status: registration, activation, reciprocal connection and built-in conformance execution implemented in `partnerapp`, 2026-10-18. Collaborators and usage rollups below remain design targets. Companion to [`partner-integration-spec.md`](partner-integration-spec.md).
Goal: a partner that has implemented the spec registers itself, passes automated checks, and goes
live the moment a Musecat operator presses **Approve**. No per-partner negotiation, no manual
environment-variable editing, no redeploy.

## 1. Outcome

| Today | Target |
| --- | --- |
| Operator hand-edits `MUSECAT_OAUTH_CLIENTS`, `MUSECAT_EXTERNAL_PROVIDERS`, `MUSECAT_JOINT_PARTNERS`, restarts | Partner submits the spec §8 onboarding form in the Developer Center; approval writes DB records that the runtime reads |
| Secrets exchanged over chat | Direction-A secret generated by Musecat and shown once; partner-issued credentials entered by the partner and encrypted at rest |
| "Is it live?" asked in Discord | Status page per application: draft → submitted → checks → approved/active → suspended |
| Contract clarified per partner | Spec is fixed; the form only collects values; the conformance kit proves compliance |

Approval is one operator action per application and environment. Each Musecat deployment
(development, production) hosts its own Developer Center, so "environment" is implicit.

## 2. Actors and permissions

| Actor | Can |
| --- | --- |
| Any active Musecat user | Create a partner application draft, edit it, submit it, see its status, rotate its own partner-issued credentials, view usage |
| Application collaborators | Same as owner for that application (invited by Musecat username) |
| Operator (`developer` tag; `moderator` read-only) | View queue, run checks, approve, reject with reason, suspend, reinstate, see audit log |
| Partner servers | Use the resulting OAuth client / provider / joint registration exactly as the spec defines; no Developer Center API |

Ownership of an application is a Musecat user, not an organization. A compromised owner account
is handled by suspension; suspension is instant and global.

## 3. Data model

New collections, all with raw REST rules locked (custom API only), following the existing
external-connection conventions.

### `partner_application`

| Field | Notes |
| --- | --- |
| `partner_id` | `^[a-z][a-z0-9_-]{0,127}$`, globally unique, immutable after approval |
| `owner` | relation → `user`, required |
| `collaborators` | relation → `user`, multi |
| `display_name`, `description` | JSON `{ko,en,ja}`; `en` required |
| `contact_email` | hidden from public; used for incident notices |
| `status` | `draft`, `submitted`, `checks_failed`, `approved`, `suspended`, `rejected` |
| `submitted_form` | JSON: the spec §8 document as submitted (secrets stripped) |
| `approved_form` | JSON: the form that is currently live; `null` until first approval |
| `approved_hash` | SHA-256 of `approved_form`; equals the OAuth client fingerprint / provider config hash the runtime uses |
| `approved_by`, `approved_at`, `reviewed_note` | audit |
| `direction_a_secret_hash` | Musecat-generated client secret, hashed; plaintext shown once |
| `direction_b_credentials` | encrypted JSON `{musecat_client_id, musecat_client_secret}` (partner-issued) using `MUSECAT_CONNECTION_ENCRYPTION_KEY` |
| `joint_keys` | encrypted JSON `{musecat_to_partner, partner_to_musecat_hash, previous_*, rotation_until}` |
| Check history | Stored in the separate locked `partner_conformance_run` collection (see §6); not a partner-uploaded claim |
| `created`, `updated` | autodate |

### `partner_application_event`

Immutable audit rows: `application`, `actor`, `kind` (`created`, `submitted`, `checks_run`,
`approved`, `rejected`, `suspended`, `reinstated`, `secret_rotated`, `key_rotated`,
`form_changed`), `detail` JSON (no secrets), `created`.

### `partner_application_usage` (daily rollup)

`application`, `day`, `direction_a_requests`, `direction_a_errors`, `direction_b_fetches`,
`joint_attempts`, `joint_connected`, `revocations_sent`, `revocations_received`. Shown on the
partner's status page and used for abuse review. No per-user rows.

Existing tables reused unchanged: the OAuth `registration` table (epoch/config hash) keeps
guarding tokens; `external_joint_connection` keeps coordinating attempts.

## 4. Runtime: approved record → live registration

The three managers (`delegation.Manager`, `connections.Manager`, `connections.JointManager`) are
built today from environment JSON at startup. The Developer Center introduces a **registry
provider** interface that both sources implement:

```
type PartnerRegistry interface {
    OAuthClients()     []delegation.Client
    ExternalProviders() []connections.Provider
    JointPartners()    []connections.JointPartner
    Version()          string // changes whenever any approved application changes
}
```

- `EnvRegistry` wraps the current environment variables (kept for bootstrap and for Musecat's own
  first-party clients).
- `ApplicationRegistry` reads `partner_application` rows with `status = approved`, decrypts
  Direction-B credentials and joint keys, and maps `approved_form` to the three config types using
  the spec §8 field names. `partner_id` becomes the OAuth client ID, the provider ID and the joint
  partner ID.
- `MergedRegistry` concatenates both; duplicate IDs fail closed (the application cannot be approved
  if an env entry already uses that `partner_id`).

Hot activation without restart:

1. Managers become swappable behind an atomic pointer (`managers.Load()`), rebuilt from the merged
   registry whenever `Version()` changes.
2. Approval, suspension and reinstatement run inside one transaction: update the application row,
   write the audit event, call `delegation.SynchronizeClients` for the new client set (which assigns
   a fresh epoch to changed/added clients and disables removed ones), then publish the new
   managers after commit.
3. Existing invariants hold automatically: a changed `approved_hash` means a new fingerprint, so
   earlier grants for that client are invalidated exactly as an env change does today; suspension
   disables the registration row, so `clientHash` returns 503 and every token stops working.
4. Multi-instance deployments poll `Version()` (a single row in `partner_registry_version`) every
   30 seconds and rebuild when it differs; approval therefore propagates within 30 seconds without
   coordination. A restart always rebuilds from the database.

Configuration precedence: env entries are authoritative for their IDs and cannot be edited in the
UI. New third-party partners are expected to live only in the database.

## 5. Approval pipeline

```
draft ──submit──▶ submitted ──automated checks──▶ ready for review ──Approve──▶ approved (live)
                      │                               │                           │
                      └─ checks_failed (partner fixes) └─ Reject (reason)          ├─ Suspend ──▶ suspended ──Reinstate──▶ approved
                                                                                  └─ partner edits form ──▶ submitted (new version; live version stays until re-approved)
```

### 5.1 Validation on submit (synchronous, partner sees errors inline)

- Form matches `musecat-partner-onboarding/v1` schema; all URLs HTTPS, no query/fragment/userinfo.
- `partner_id` unique and not reserved; display names present.
- `services[].id` exist in the spec §1.1 registry.
- Direction A: 1–8 redirect URIs, exact strings.
- Direction B present ⇒ all five endpoints plus `records_url`, `identity_scope`, ≥ 1 service.
- `joint.enabled` ⇒ `direction_b` present, `joint_url`, `connect_start_url`, ≥ 1 manifest Musecat supports, partner-issued `musecat_to_partner_key` ≥ 32 bytes.
- Partner-issued secrets are accepted only on submit/rotate, encrypted immediately, never echoed.

### 5.2 Automated checks (implemented)

Owners and active reviewers can run checks in the app's Developer Center panel. The run is
persisted, starts within one minute, and the panel polls results and retains the latest ten
reports. One run per application, three active runs per actor and a one-minute cooldown apply.
The submitted form and credential revision identify the exact configuration tested. Changed
settings or reports older than 30 days are shown as stale. A run's progress, timestamps and
individual pass/fail/action_required/not_applicable cases remain visible separately.

The server tests callback TLS/reachability, optional RFC 8414 metadata, rejection of unauthenticated
token/revocation/userinfo/records calls, rejection of PKCE plain, joint bearer enforcement,
partner-key provisioning, invalid/expired/consumed intents, unsupported manifests, unknown
generations and idempotent revocation requests. Redirects are never followed. A PKCE error redirect
counts only when its callback and state match the generated probe; login screens remain unverified.

Optional staging fixtures enable userinfo subject/issuer verification, typed public and private
record envelopes, and refresh/revoke/rejected-reuse checks. Use dedicated test accounts and a
separate disposable refresh family. Revocation requires the explicit destruction checkbox. Both
servers' live joint grants are checked using an owner-supplied attempt ID from the normal consent
flow; the checker never fabricates consent or grants. Missing fixtures or interactive requirements
are action_required and keep the run incomplete. Raw fixtures and response bodies never appear in
reports. Fixtures are encrypted while queued and erased after processing or interrupted-run recovery.

### 5.3 Approve (the one click)

Current behavior: operators review the measured reports and approve separately. A successful
check does not auto-approve. Initial approval may be needed to provision a normal joint test
connection; unresolved cases remain explicit in the panel. The following activation design
describes the existing independent approval action:

1. `approved_form := submitted_form`, `approved_hash` recomputed, `status := approved`.
2. If Direction A is new or its redirect URIs/scopes changed: generate a new client secret, store
   its hash, display plaintext **once** to the operator *and* on the partner's status page for
   15 minutes (one-time reveal link bound to the owner session). Existing grants are invalidated by
   the fingerprint change; the partner is told to expect reconnection.
3. If joint is enabled: generate `partner_to_musecat_key`, same one-time reveal.
4. Write the audit event, synchronize registrations, bump registry version.
5. Notify owner and collaborators (in-app notification + contact email).

Reject: `status := rejected` with a note; the partner may edit and resubmit.
Suspend: immediate; all Direction-A tokens fail with 503, Direction-B fetches and joint endpoints
return `unauthorized_partner`; outstanding joint attempts are cancelled; users see the connection as
`invalidated` in their settings. Reinstate restores the same `approved_form` without a new secret.

### 5.4 Changes after approval

Any edit creates a new `submitted_form` and reruns checks while the previous `approved_form`
stays live. Approving the change swaps versions. Field-level consequences are shown to the partner
before submit:

| Change | Consequence |
| --- | --- |
| Display name, description, contact | None |
| Direction-A redirect URIs | New fingerprint → users must reconnect |
| Direction-B endpoints, scopes, services | New provider config hash → existing connections become `invalidated`; joint pairs `degraded` |
| Joint URLs, manifests | Joint attempts restart; existing pairs unaffected until next action |
| Partner-issued credentials/keys | Rotation window per spec §4; no user impact |

## 6. Built-in conformance runner (implemented)

The Developer Center now runs conformance checks directly on the Musecat server. Partners do not
need to install a binary, upload a Markdown file, or self-sign a claimed result. The server produces
`musecat-conformance/v1` reports from actual probes, with bounded codes and no remote payloads.
This replaces the earlier proposed HMAC report upload: a partner-authored report is not treated
as proof that a remote test ran. The same runner and cases are exercised against scripted partner
fixtures in Core tests. Browser/BFF tests cover access checks, secret projection, result state and
one-use fixture entry. Full owns the independent locked run-table migration and worker schedule.

Use the app detail's **Run / rerun checks** action for basic checks. Expand **Provide test fixtures**
for live staging data checks; the field descriptions identify the inputs. After normal joint consent,
copy the attempt ID from the joint connection list into the test fixture. To test a partner that
requires login before validating PKCE, complete its interactive PKCE rejection test separately;
the UI keeps that item unverified instead of accepting a login page as proof. No check creates
or transfers user authorization.

Routes under `/{locale}/developer`:

| Route | Content |
| --- | --- |
| `/developer` | Existing public docs; adds "Register an application" |
| `/developer/apps` | My applications: status badges, last check result, usage sparkline |
| `/developer/apps/new`, `/developer/apps/{id}` | Form editor mirroring spec §8 with inline validation and consequence warnings; file upload for the conformance report; collaborator management |
| `/developer/apps/{id}/credentials` | One-time reveal of Musecat-issued secret/key; rotate partner-issued credentials |
| `/developer/apps/{id}/events` | Audit timeline |

Operator routes under `/{locale}/moderation/developer`:

| Route | Content |
| --- | --- |
| `/moderation/developer/apps` | Queue filtered by status; checks summary; **Approve / Reject / Suspend** |
| `/moderation/developer/apps/{id}` | Full form diff (live vs submitted), check details, conformance report, usage, events |

All pages are session-authenticated through the WebCore BFF; secrets never reach the browser
except through the one-time reveal response, which is `no-store` and not logged.

## 8. API surface (Core custom API)

User session (owner/collaborator):

| Method and path | Behavior |
| --- | --- |
| `GET /developer/apps` | List own applications |
| `POST /developer/apps` | Create draft `{partner_id, display_name, …}` |
| `GET /developer/apps/{id}` | Detail incl. submitted/approved forms (secrets stripped), checks, usage |
| `PUT /developer/apps/{id}` | Update draft/submitted form; partner-issued secrets accepted here and encrypted |
| `POST /developer/apps/{id}/submit` | Validate and set `submitted`; checks are queued separately by the explicit run action |
| `POST /developer/apps/{id}/rotate` | Rotate partner-issued credentials (`direction_b` or `joint`) with rotation window |
| `GET /developer/apps/{id}/reveal/{token}` | One-time reveal of Musecat-issued secret/key |
| `GET /developer/apps/{id}/checks` | Safe conformance history |
| `POST /developer/apps/{id}/checks` | Queue server-measured conformance checks with optional sealed staging fixtures |
| `PUT /developer/apps/{id}/collaborators` | Replace collaborator list |
| `GET /developer/apps/{id}/events` | Audit timeline |

Operator (`RequireAdminAccess`, developer tag):

| Method and path | Behavior |
| --- | --- |
| `GET /moderation/developer/apps` | Queue with filters |
| `POST /moderation/developer/apps/{id}/checks` | Re-run automated checks |
| `POST /moderation/developer/apps/{id}/approve` | §5.3 |
| `POST /moderation/developer/apps/{id}/reject` | `{note}` |
| `POST /moderation/developer/apps/{id}/suspend` | `{note}` |
| `POST /moderation/developer/apps/{id}/reinstate` | |

All responses `no-store`. Rate limits: 30 writes per 10 minutes per user on `/developer/apps/*`;
checks are queued, at most one run per application in flight. Routes are **not** part of the
`account:access` allowlist: a connected partner app cannot manage applications.

## 9. Security notes

- Musecat-issued secrets: 32 random bytes, stored as hashes, revealed once, rotated only through
  approval (new secret) or an owner-initiated rotation that also bumps the fingerprint.
- Partner-issued secrets and keys: AES-GCM with `MUSECAT_CONNECTION_ENCRYPTION_KEY`; a key change
  invalidates all Direction-B/joint registrations until partners re-enter credentials (same rule
  as the existing provider credentials).
- Automated checks are SSRF-guarded: declared hosts are resolved and rejected if they map to
  loopback, link-local, private or metadata ranges; connections pin the resolved address.
- `partner_id` is immutable after approval because it is embedded in grant subjects, provider
  identities and joint ledgers.
- Operators cannot see partner-issued secrets; they see only whether one is present and when it
  was last rotated.
- Owner account withdrawal with an approved application: the application is suspended and the
  collaborators are notified; a collaborator can claim ownership through an operator action.
